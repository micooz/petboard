# `.ANM` 动画格式规范（v1）

本文是 `.ANM` 的**唯一权威描述**。格式实现**只有一份**（`crates/anmfmt`），板子直接用它，
网页经 `crates/wasmfmt` 编成 WASM 用同一份。

| 位置 | 作用 |
|---|---|
| `crates/anmfmt/` | 格式的**权威实现**：定义 + 打包（`encode_rasters` 做帧差分）+ 解析（`decode_prefix` / `validate`） |
| `crates/wasmfmt/` | WASM 门面：平铺数组 ↔ 帧序列的搬运、错误原样出口；产物由 `pnpm wasm` 生成后随仓库跟踪（改格式 crate 要重生成并一起提交） |
| `web/src/lib/encode/` | 网页侧薄壳：GIF / WebP 解码与切片、JS 形状 ↔ 平铺数组、中文错误文案 |
| `crates/fm-core/src/commands/playback.rs` | 固件侧：解码 + 合成到画布 + 刷屏 |

## 1. 总览

- **用途**：给 ESP32 板子顺序播放的动画格式。GIF / WebP 的解码、透明合成、缩放都在电脑侧完成，
  板子只按位图搬像素，**不在单片机上跑图片解码器**。
- **后缀**：卡上用 `.ANM`。FAT 8.3 的扩展名最多 3 个字符。
- **magic**：`ANM\0`（4 字节），后跟版本号。
- **字节序**：所有多字节整数都是小端。
- **像素格式**：RGB565，小端（同一个像素在文件里是低字节在前）。

## 2. 文件头（18 字节）

| 偏移 | 长度 | 字段 | 说明 |
|---:|---:|---|---|
| 0 | 4 | magic | `ANM\0` |
| 4 | 1 | version | 当前为 `1` |
| 5 | 1 | flags | 必须为 0 |
| 6 | 2 | canvas_width | 画布宽（像素） |
| 8 | 2 | canvas_height | 画布高（像素） |
| 10 | 2 | frame_count | 帧数 |
| 12 | 4 | total_len | 整个文件的字节数 |
| 16 | 2 | reserved | 必须为 0 |

## 3. 帧

每帧 = **帧头（12 字节）** + **位图** + **颜色**。

| 偏移 | 长度 | 字段 | 说明 |
|---:|---:|---|---|
| 0 | 2 | delay_ms | 这一帧显示多久（毫秒） |
| 2 | 2 | x | dirty bbox 左上角 x（相对画布） |
| 4 | 2 | y | dirty bbox 左上角 y |
| 6 | 2 | width | bbox 宽；**宽或高为 0 表示这一帧没有要画的像素**（只延时） |
| 8 | 2 | height | bbox 高 |
| 10 | 1 | flags | 必须为 0 |
| 11 | 1 | reserved | 必须为 0 |

- **位图**：`((width + 7) / 8) * height` 字节，行优先；每行 `(width + 7) / 8` 字节，
  **高位在前**（bit7 = 该行最左像素）。每行最后一个字节里超出 `width` 的补齐位必须是 0。
- **颜色**：位图里每个 `1` 对应一个 RGB565 小端，按行优先顺序排列。
  个数 = 位图里 1 的个数 = `popcount(bitmap)`。

### 3.1 位图的语义

位图**精确**表示"这一帧哪些像素变了"，颜色只存这些像素。也就是说：

- **无损**：解码后的画布与源动画逐像素一致，没有任何量化。
- 代价是每帧要传 `bbox 面积 / 8` 字节的位图，所以 bbox 越大越亏；对"变化像素少但分布很散"的
  内容，位图不如按行分段便宜（实测 cat.gif 上净赚 33%）。

### 3.2 第 0 帧（复位帧）

第 0 帧**只画自己的非黑像素**，不负责擦掉上一轮留下的残影。

前提（解码方必须遵守）：**每一轮开始前把画布清零**。固件在每轮开头 `canvas.fill(0)`
（100KB memset，几十微秒）；这样第 0 帧就退化成普通帧，和后续帧走同一条路径。

⚠️ **光清画布（RAM）不够**：屏幕上的像素是**按每帧的 dirty bbox 一块块推过去**的，
上一轮在"第 0 帧 bbox 之外"画过的像素不会自己消失。渲染器必须把上一轮真正画过的**并集矩形**
擦成黑的（画布和屏幕都要）。擦的时机也有讲究：等下一轮的第一帧**解进画布、真要画了**再擦，
而且只擦该帧 bbox **之外**的那几块。擦早了会先黑一块再等读卡（换轮"黑闪"）；整块擦会把刚画好的
第 0 帧一起擦掉，于是又得再画一遍。

> 第 0 帧只画自己的非黑像素能省下大量体积：整块重写并集矩形要占掉整个文件约 31%，
> 而且那一帧自己做起来最慢。

## 4. 校验规则

打包方（`anmfmt::check_frame` / 网页 `validateAnm`）：

- bbox 必须落在画布内（`x + width <= canvas_width`、`y + height <= canvas_height`）；
- `bitmap.len() == ((width + 7) / 8) * height`；
- `colors.len() == popcount(bitmap) * 2`。

解码方（固件 `media/play` 的播放循环）：

- magic / version / flags / reserved 检查，`total_len` 必须等于实际文件长度；
- 每帧的 flags / reserved 必须为 0，bbox 必须落在画布内；
- 颜色字节按 `popcount(bitmap)` 读取 —— 位图里点亮的位个数决定要读多少颜色。

**版本必须完全相等**：固件只认 v1，对不上直接报 `unsupported ANM version (need v1)`；
网页解到版本不符的文件时提示"重新上传素材"。

## 5. 一个真实的例子

一个 4x4、两帧、每帧 40ms 的文件（第 1 帧左半边红 `f800` 右半边绿 `07e0`，
第 2 帧左半边改成蓝 `001f`）：

```text
0000  41 4e 4d 00 01 00 04 00 04 00 02 00 62 00 00 00  ANM.........b...
0010  00 00 28 00 00 00 00 00 04 00 04 00 00 00 f0 f0  ..(.............
0020  f0 f0 00 f8 00 f8 e0 07 e0 07 00 f8 00 f8 e0 07  ................
0030  e0 07 00 f8 00 f8 e0 07 e0 07 00 f8 00 f8 e0 07  ................
0040  e0 07 28 00 00 00 00 00 02 00 04 00 00 00 c0 c0  ..(.............
0050  c0 c0 1f 00 1f 00 1f 00 1f 00 1f 00 1f 00 1f 00  ................
0060  1f 00                                            ..
```

逐段读：

| 偏移 | 内容 |
|---|---|
| `0000` | magic `ANM\0`、version 1、flags 0 |
| `0006` | 画布 4x4、帧数 2、总长 98（`0x62`） |
| `0012` | 第 1 帧：`delay 40ms`、bbox (0,0,4,4)、flags 0 |
| `001e` | 位图 4 字节 `f0 f0 f0 f0`（4 行 × 1 字节，每行高 4 位置位） |
| `0022` | 颜色 16 个：`f800 f800 07e0 07e0` × 4 行（左红右绿） |
| `0042` | 第 2 帧：`delay 40ms`、bbox (0,0,2,4)、flags 0 |
| `004e` | 位图 4 字节 `c0 c0 c0 c0`（每行高 2 位置位 = 只画左半边） |
| `0052` | 颜色 8 个：`001f` × 8（蓝） |

这份文件播几轮？**文件里没有答案**：卡上 `data/PLAYLIST` 里写 `CAT.ANM 3` 就播 3 轮，
写 `CAT.ANM 0` 就一直播到被 `media/stop` 打断。
